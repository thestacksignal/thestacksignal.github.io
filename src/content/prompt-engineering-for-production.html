Key takeaways

  • A production prompt is an interface contract between your application and the model — it needs versioning, testing and failure handling like any other interface.
  • Structured output (JSON schemas, function calling) removes an entire class of parsing failures that free-text prompting invites.
  • Few-shot examples usually beat longer instructions for teaching format and edge-case handling.
  • Without an evaluation set, you cannot tell whether a prompt change is actually an improvement — you can only tell that it changed.

A prompt that works well in a chat window is a different artifact from a prompt embedded in a production system. In a chat window, a slightly malformed response is something a human reads past. In production, that same malformed response is a parsing exception, a broken downstream field, or a silently wrong record in a database. The gap between those two contexts is exactly what production prompt engineering has to close.

Structured output: remove the parsing problem entirely

Asking a model to "return the result as JSON" in free text invites markdown fences, explanatory preambles, and inconsistent field names. Modern APIs offer two better options:

ApproachWhat it guarantees
JSON schema / structured output modeThe response conforms to a defined schema — no fences, no missing fields, no type mismatches
Function/tool callingThe model emits a structured call with typed arguments instead of narrative text
Free-text parsing with regexNothing — this is the fallback when neither option above is available, and it should be treated as fragile
✓

If your API supports a native structured-output or function-calling mode, use it instead of instructing the model to "output valid JSON only" in the prompt text. The native mode is enforced at generation time; the instruction is just a request the model can still ignore under pressure.

Examples beat instructions for format and edge cases

Explaining a desired output format in prose is less reliable than showing two or three examples of input-output pairs, especially for edge cases: how to handle a missing field, an ambiguous category, or an empty result. A well-chosen example does the work of several paragraphs of instruction, and it generalizes better to inputs the instruction didn't anticipate.

!

Watch out: examples teach pattern-matching, including patterns you didn't intend. If every example in your few-shot set happens to have a non-empty result field, don't be surprised when the model struggles to produce an empty one for a genuinely empty case.

Designing for failure, not just success

  • Give the model a way to say "I don't know" or "not enough information" — explicitly, as a valid output. Without this option, an uncertain model tends to guess rather than flag the uncertainty.
  • Validate output against the schema before it reaches downstream code, and define what happens on a validation failure — retry, fall back to a default, or surface an error, but decide this deliberately rather than letting a malformed response propagate.
  • Set explicit boundaries on scope — a support-ticket classifier should have a defined behavior for a ticket that doesn't fit any category, not silently force-fit it into the closest one.

Prompts need version control and evaluation, not just iteration

A prompt change that "feels better" on the five examples you happened to test is not evidence of improvement. Treat prompts the way you'd treat any other piece of logic that affects production behavior.

  1. Version every prompt — a prompt change is a code change, and should be tracked, reviewed and attributable in the same way.
  2. Build a small evaluation set — 20 to 50 representative inputs with known-good outputs, covering both common cases and known edge cases.
  3. Run the evaluation set on every prompt change before shipping, and compare against the previous version, not just against intuition.
  4. Watch for regressions on old cases when fixing a new one — prompt changes frequently trade one failure for another rather than net-improving.

This evaluation discipline is the same one that applies to evaluating an embedding model choice or a retrieval pipeline — measure against your own representative cases, not vibes or a public leaderboard.

Where prompts fit next to agents and RAG

In a RAG system, the prompt is the contract for how retrieved context gets used and cited. In an agentic system, the prompt additionally has to specify when to call a tool, how to interpret its result, and when to stop. The more the prompt is asked to do, the more essential structured output and explicit failure paths become — free-text instructions scale poorly as responsibility grows.

A production prompt is an interface contract, not a magic sentence. Treat it with the same rigor you'd apply to any other interface your system depends on.

The prompts that survive contact with production are the ones designed around failure from the start — structured output, explicit uncertainty handling, and a real evaluation set — not the ones that happened to produce a good-looking answer once.
